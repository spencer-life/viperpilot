Product roadmap · ViperPilot · 2026-09-29

Build a better daily workflow for the Viper V4 Pro.

A lightweight native Windows control app: inspect device state, choose a profile, edit proven controls, and recover safely when a change fails. Product work moves by evidence and exit gates, not calendar estimates.

Measured scope today

One wireless V2 identity: 1532:00e6 · firmware 1.4 · MI_03. The two built-in profiles, a forced 1600→1600 DPI setter, wireless 1000↔4000 Hz polling, Mouse4/Mouse5 assignments, tray/status app, hotkey, process exit, and power-cycle behavior have recorded tests in README.md. DPI remains fixed at 1600; changed values are not proven. Battery and power values remain GET-only.

Product promise: Compare launch, idle cost, and profile switching against the official Razer app on the same machine and device before making speed or resource claims. Feature parity is never assumed.

Delivery sequence

Milestones follow dependency order. Each closes only when its exit criteria and release gates pass; later research is not required to ship an earlier milestone.

Shipped / measured recorded implementation and result Planned product or engineering work Hardware-gated requires field-level hardware evidence Research protocol discovery; no write support implied Blocked ship only after stated gate

  1. M0 / FOUNDATION

    Shipped · measured

    Preserve the measured core

    • Keep Developer and Gaming profiles as known-good recovery choices; preserve the immutable first baseline and diagnostic history.
    • Fail closed on unsupported identities, unknown raw states, and unmeasured polling transitions. Wired remains a recovery investigation.
    • Stay single-instance and idle without polling. No browser runtime, service, driver, interception, or injection without separate review and measured need.

    Exit evidenceSupport and limits trace to recorded runs in README.md; package checks and cross-builds stay green.

  2. M1 / CONTRACT

    Next · planned

    Define configuration and write contract

    • Typed field allowlist, ranges, device/transport support; separate profile intent from raw bytes and reject unsupported combinations before planning.
    • Version local config. Define V1 migration, atomic save, corrupt/stale handling, recovery, and rollback copy; never touch the immutable hardware baseline.
    • Make plans inspectable: identity, changed fields, packet intent, expected readback, recovery path, and journal location. Preview is not proof.
    • Offline fixtures for valid, malformed, stale, and cross-device data; prove unsupported setters are unreachable.

    Exit gateReversible migration; invalid input fails before planning; protocol, config, plan, and rollback suite passes offline.

  3. M2 / PROFILES

    Hardware-gated

    Editable profiles for proven fields

    • Create, name, duplicate, edit, select, and delete user profiles. Built-ins stay read-only measured presets.
    • Keep DPI fixed at 1600 until each exposed changed value/range and material combination has evidence for a write, independent readback, and baseline restoration. Then expose only the M1-supported DPI contract, measured wireless 1000/4000 Hz pair, and evidenced Mouse4/Mouse5 actions.
    • Preview all changes; journal, independently GET each changed field, report partial failure and recovery without premature success.
    • One logical field per experiment: immutable baseline, full VID/PID and serial review, exact plan, suffix guard, readback, restore before next field.

    Exit gateEvery field has protocol evidence, recorded write/readback/restore. Profiles pass switching, interrupted-write recovery, process-exit, and power-cycle tests. Unevidenced fields stay unavailable or read-only.

  4. M3 / DAILY FLOW

    Planned

    Fast desktop workflow

    • Focused dashboard for identity, connection, available battery, current DPI/polling/profile, plus clear stale/unknown states and reachable profile action.
    • Profile list/editor, explicit unsaved state, keyboard and focus flow, readable errors, recovery guide. Document in Figma, then capture the running UI for visual QA.
    • Measure cold/warm launch, idle CPU/memory, switch time, and clicks/steps. Record machine, OS, firmware, connection, Synapse state, samples, and method. Unproven target: at least 2× faster median cold launch to actionable UI and fewer user actions to switch an existing profile; report device commit latency separately.
    • Keep package size and steady-state work in release review; prefer native controls and event-driven updates unless measurements justify more.

    Exit gateKeyboard/screen-reader, high-DPI/narrow-window, idle, benchmark record against the target, and visual QA pass. No speed claim without reproducible comparison.

  5. M4 / PORTABILITY

    Planned

    Profile library and distribution

    • Define portable vs identity-bound fields. Validate schema, ranges, transport, and provenance before import offers a plan.
    • Imported files never carry a trusted baseline or authorize writes. Add device association only after identity semantics stabilize.
    • Test malformed, stale, future-version, and cross-device files offline.
    • Review install/update/uninstall, config rollback, diagnostics export, and recovery to last verified profile. Startup stays opt-in until its gates pass.

    Exit gateRound-trip, migration/downgrade/recovery fixtures, clean install/update/uninstall, and documented rollback pass. No automatic cross-device application.

The measured baseline is narrow by design: wired 4000 Hz, other Razer models, arbitrary assignments, and user-editable profiles are not currently supported.

Independent research track

Candidates do not promise controls. A GET result or source inspection alone never enables a setter.

Candidate controls

Research stays separate from the delivery sequence.

  • DPI stage count and valuesResearchExact encoding and range; one field at a time with independent readback and baseline restoration.
  • Additional button assignmentsResearchPer-action raw mapping, OS behavior, persistence, and rollback. No arbitrary raw editor.
  • Battery, idle sleep, low-power thresholdGET-only / researchSetter protocol, supported range, and persistence. Optional reads are not setter evidence.
  • Sensor optionsResearchIdentify real fields and firmware behavior before designing controls.
  • Wired setup or 4000 HzBlockedSeparate wired identity, transport, and polling-transition evidence.
  • Other mouse modelsBlockedPer-model capability matrix and independent baselines/tests. Similarity does not confer support.

For each proposal, record: date; full device, firmware, and transport identity; starting raw state; source hypothesis; GET discovery; exact single-field plan; independent readback; restore; relevant process-exit and power-cycle persistence; linked report files. Stop on ambiguous identity or state. Treat each setter as a possible flash write.

Release decision gates

Apply the relevant checks before shipping a milestone.

  1. Offline correctness — protocol, config, migration, validation, plan, rollback, and UI logic via the repository mise.toml tasks and pinned Windows cross-build tools.
  2. Hardware safety — complete immutable baseline, reviewed full identity, exact plan, one-field experiment, independent readback, verified restore. No apply/restore from planning or design tasks.
  3. Regression — both complete built-in profiles, production hotkey, process exit, and mouse power-cycle pass after relevant changes. Tray startup stays off until documented gates pass.
  4. Product quality — accessibility, visual QA, installation rollback, and measured performance meet the milestone's criteria.
  5. Claims — README.md lists only evidenced support and conditions. Candidates stay planned, research, or blocked until gates pass.

Definition of a release

Evidence closes the gate.

The roadmap advances when the recorded conditions support it. Dates, protocol guesses, and visual previews do not count as proof of device support.

  1. Offline correctness. Checks run through the repository's mise.toml tasks and pinned cross-build workflow.
  2. Hardware safety. Full identity, immutable baseline, exact one-field plan, independent readback, and restoration recorded.
  3. Regression. Complete built-in profiles, hotkey, exit behavior, and power-cycle behavior revalidated when relevant.
  4. Product quality. Accessibility, visual QA, rollback, and performance meet the milestone's exit criteria.
  5. Claims. Documentation and release notes state only evidence-backed support and measured conditions.
